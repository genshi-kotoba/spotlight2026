# 随机种子系统调用说明（PRG-005）

**状态：已实现的调用手册，协议 v1。** `SeedService` 已配置为工程 Autoload，`RandomStream`、`RandomDomains` 和 `SeedRegistry` 已实现。文中的调用代码放在各业务流程的方法内执行；不要把新局初始化放到每个场景的 `_ready()` 中。

适用范围：21 天 Game Jam；单机、Godot / GDScript、三位程序协作。工程基线 `42b9fca`，本模块于 2026-10-05 实现；验证环境为 **Godot 4.7.2.stable.official.ed1daf0bf（macOS）**。地图、战斗、商店、奖励等正式业务仍需各负责人按本文接入。

PRG-005 采用**一个主种子，按稳定地址按需派生、缓存随机流**的方案。`reference/card-and-dice/docs/可复用代码清单.md` 中“固定派生 50 个子种子”保留为原始参考，本任务按本文准备接口。动态指调用时创建尚不存在的流；主种子在同一局中保持不变。

地图玩法以项目负责人的 2.5D 要求为准：每个六边形坐标一个可通行地块，高度为表现属性。现有 3D 演示的高差通行规则不约束本接口；地图改造由地图负责人另行处理。

## 1. 队友先看这部分

每种随机业务只需要确定三项：**用途 `domain`、稳定身份 `ids`、次数 `occurrence`**。服务负责派生种子、持有流和恢复进度，不要求申请子种子编号或预留数量。

```gdscript
# 以下为业务方法内的调用示例。
# 单局负责人在新局启动时调用一次；各业务模块不调用 begin_run。
var main_seed = SeedService.begin_run("jam-demo-001")

# 商店负责人：为指定地图、指定节点的首次商品生成取得独立流。
var shop_rng = SeedService.get_stream(
    RandomDomains.SHOP, ["map-001", "hex:2,-1"], 0
)
var item_id = shop_rng.pick(["item_001", "item_002", "item_003"])

# 新增业务：统一商定域名和身份后即可调用，不改服务的派生算法。
var alchemy_rng = SeedService.get_stream(
    &"alchemy.result", ["map-001", "event-017"], 0
)
```

正常调用前要确认业务输入有效；本节为可读性省略失败处理，正式失败约定见第 4 节。

三个必须遵守的行为：

1. **同地址拿到同一个流，并继续推进。** 重复 `get_stream()` 不回到初始序列，也不会每次返回同一个结果。
2. **随机结果由业务保存。** 商店已经生成的商品、奖励候选、洗好的牌序等应存入局内数据；打开 UI 展示这些数据。
3. **换新身份才表示新的随机过程。** 买东西、打开界面不增加 `occurrence`；被玩法认可的刷新、再战等才增加对应业务次数。

例如：先访问 A 店再访问 B 店，与先 B 后 A，在两店的池、权重、玩家条件和各自调用步骤相同时，两店商品各自不变。刷新 A 店不会推进 B 店或战斗抽牌流。玩家状态变化导致商品池改变时，结果允许变化。

## 2. 为什么本次采用动态派生

| 比较项 | 固定 50 个子种子 | 按稳定地址按需派生 |
| --- | --- | --- |
| 新增系统、节点、刷新次数 | 需要分配名额并说明编号含义 | 新域或新地址即可，不改服务核心 |
| 三位程序协作 | 维护共享编号表，避免误用同一编号 | 维护域名与业务身份约定 |
| 不同访问顺序 | 正确的固定映射也能支持；按请求顺序分配则会出问题 | 地址直接决定初始流，创建顺序不参与派生 |
| 实现成本 | 派生表、映射表和流状态管理 | 一个地址编码函数、派生函数与缓存；同样要保存流状态 |
| 上限和资源 | 50 是人为额度，扩充时要调整 | 仅创建用到的流；新局清空，局内保留创建过的状态 |

**本项目推荐动态方案，因为业务范围尚在扩展，固定额度没有明确用途。** 固定 50 并非错误，也不是随机质量较差；若其映射稳定，同样可以隔离子系统。动态方案的收益在扩展与调用约定，不能替代业务数据管理。

此处“流互不干扰”指各地址分别持有状态，一处取数不推进另一处。哈希派生用于混合输入，不宣称所有不同地址的数值永不重复、有限种子空间绝无碰撞或已经证明数学独立。

## 3. 地址怎么填写

### 3.1 建议的第一批域

以下是接入约定，不表示这些玩法已经完成。需要的新域可以补进常量与本文，不要求在服务里注册 50 个位置。

| 常量 / 域名 | `ids` 顺序 | `occurrence` 含义 | 业务数据负责人 |
| --- | --- | --- | --- |
| `MAP_LAYOUT` / `map.layout` | `[map_id]` | 布局生成第几次尝试，首次为 0 | 地图 |
| `MAP_NODES` / `map.nodes` | `[map_id]` | 节点分配第几次尝试，首次为 0 | 地图 / 单局 |
| `ENCOUNTER` / `encounter` | `[map_id, node_id]` | 第几次遭遇生成，首次为 0 | 遭遇 |
| `BATTLE_DRAW` / `battle.draw` | `[map_id, node_id, battle_index]` | 默认 0；整场持续使用同流 | 战斗 / 牌组 |
| `BATTLE_LOGIC` / `battle.logic` | `[map_id, node_id, battle_index]` | 默认 0；怪物随机与其他战斗随机 | 战斗 |
| `REWARD` / `reward` | `[map_id, node_id, reward_kind]` | 该类奖励的产生或刷新次数 | 奖励 |
| `SHOP` / `shop` | `[map_id, node_id]` | 商品刷新次数，首次为 0 | 商店 |
| `RELIC` / `relic` | `[map_id, node_id, purpose]` | 此用途的生成次数 | 典籍残片 |

`reward_kind`、`purpose` 使用固定业务字符串，如 `"victory"`、`"initial_roll"`，避免多个业务误用同一地址。通过商店/奖励池抽取残片时，默认使用该商店/奖励流；仅当有明确独立随机阶段时才另开 `relic` 流，不重复为同一次抽取开两个流。

一条流归一个明确的随机过程管理。需要让某阶段新增随机不影响另一阶段时，应拆域，例如 `battle.enemy_ai`；只保证域之间隔离，不保证同一流里插入一次随机后后续结果不变。

### 3.2 稳定身份

- `map_id` 是本局地图实例身份，例如 `"map-001"`；进入下一张图使用新 ID，并存档。
- `node_id` 使用地图生成时确定并保存的节点 ID，或固定格式的六边形逻辑坐标，如 `"hex:2,-1"`。位置会变化的节点应使用不随位置变的业务 ID。
- `battle_index` 是同一节点的战斗实例编号，首次为整数 `0`；只有真正创建一场新战斗才增加并保存。继续存档中的战斗沿用原值。
- 多张图复用同一坐标时，由 `map_id` 区分。需要跨地图的业务可另约定局内稳定 ID。
- 不使用 `get_instance_id()`、内存地址、场景临时名称、当前时间，或“这是玩家访问的第几个节点”作为身份。

业务 ID 必须确定性地创建并保存在业务存档中。当前地图将来无论采用手写模板还是程序生成，这条规则都适用。服务不替业务决定什么算“同一个节点”。

### 3.3 通用输入约定

- `domain`：`StringName`，小写字母开头的点分名称，段内允许小写字母、数字和下划线，如 `shop`、`battle.draw`。空名称或其他格式失败，不自动更名。
- `ids`：有序 `Array`，元素仅允许 `int`、`String`、`StringName`；字符串与 `StringName` 同义。整数 `17` 和字符串 `"17"` 是不同身份；不要混用。
- `ids` 的值保持原样，不做去空白、大小写转换或 Unicode 归一化。允许空数组表示整局共享身份，但表中已有业务按各自结构传参。
- `occurrence`：非负整数，默认 `0`。不得用全局取流次数代替。增长时机与保存归业务负责。
- 主种子：文本，先 `strip_edges()`；保留大小写与其余内容，不把数字字符串转整数。`"001"` 与 `"1"` 是不同主种子。空输入表示新生成主种子；服务返回最终文本，单局保存并供玩家复制。

增加域时只需说明：归哪个模块、ID 字段顺序、次数何时增长、结果保存在哪里。用 `RandomDomains` 常量集中维护正式域名，减少拼写导致意外新流。

## 4. 接口契约

### 4.1 `SeedService`：生命周期与取流

| 接口 | 返回 | 行为 |
| --- | --- | --- |
| `begin_run(seed_text: String = "")` | `String` | 创建新局随机上下文；清空流缓存，返回最终主种子；旧句柄失效 |
| `get_stream(domain: StringName, ids: Array, occurrence: int = 0)` | `RandomStream` 或 `null` | 首次派生并缓存；以后返回该地址原流，取流本身不取随机数 |
| `capture_snapshot()` | `Dictionary` | 返回可保存、与服务内部数据分离的快照；不推进随机流；未初始化则返回空字典并报错 |
| `restore_snapshot(snapshot: Dictionary)` | Godot `Error` | 先完整验证，成功后整体替换随机上下文并使旧句柄失效；失败保留原随机上下文 |
| `get_main_seed()` | `String` | 只读当前主种子；尚未开始或恢复一局时返回空字符串 |

`SeedService.last_error` 与 `RandomStream.last_error` 为对应对象最近一次操作的 Godot `Error`，成功为 `OK`。以当前调用的返回值为判断依据，不把上一次错误当作后续调用结果。参数错误通过 `push_error()` 提供诊断，不依赖仅在开发版有效的断言。

只有单局负责人调用 `begin_run()` 与 `restore_snapshot()`。地图、商店、奖励和战斗拿流并使用，不自行初始化主种子。新局前应结束旧局业务对象；业务数据的清理不由随机服务偷偷完成。

同一局的普通场景切换保持上下文。`RandomStream` 是按引用共享的包装对象，内部持有唯一 RNG；不复制一份状态让两个句柄独立推进，也不向业务暴露裸 RNG 的 `seed`、`state` 或 `randomize()`。

首次创建时服务复制地址参数，之后调用方修改原来的 `ids` 数组不会改掉这条流的身份。每个地址由一个业务过程统一安排消费顺序；两个模块各自持有同地址句柄会共享推进位置，不能当作两个独立流。

所有共享服务调用在 **Godot 主线程**执行；服务不提供并发锁，也不支持多线程同时消费同一随机上下文。生成/刷新/保存之间不要插入 `await` 导致同一业务被重入。未来需要后台生成时，另设计独立上下文和结果提交边界。

### 4.2 `RandomStream`：常用操作

| 接口 | 返回 | 约定 |
| --- | --- | --- |
| `int_range(min_inclusive: int, max_exclusive: int)` | `Variant`：整数，失败为 `null` | 左闭右开 `[min, max)`；`min < max`；首版限定 `min` 与 `max-1` 都在有符号 32 位范围 |
| `pick(items: Array)` | `Variant`，失败为 `null` | 等概率选择一个元素；不删除元素；非空且元素不含 `null` |
| `weighted_pick(entries: Array)` | `Variant`，失败为 `null` | 每项 `{"value": ..., "weight": ...}`；值非 `null`，权重是有限非负数，总和有限且大于 0；零权重不选中 |
| `shuffle_in_place(items: Array)` | Godot `Error` | 用本流洗牌并修改传入数组；空数组或单元素返回 `OK` 且不取数；只读数组失败 |

重复抽取是否允许重复由业务决定。`pick()` 是有放回抽样；三个不同奖励可先复制合格 ID 池，再洗牌取前三个，或每抽中一个就从本地池中删除。

```gdscript
# 初始化候选时做一次，保存结果；UI 不再次执行。
var candidates = ["card_001", "card_002", "card_003", "card_004"]
var reward_rng = SeedService.get_stream(
    RandomDomains.REWARD, ["map-001", "hex:4,0", "victory"], 0
)
if reward_rng == null:
    return  # 上层呈现生成失败，不发放/收费。
var error = reward_rng.shuffle_in_place(candidates)
if error != OK:
    return
var choices = candidates.slice(0, 3)
# 单局数据保存 choices、generated 状态及 claim 状态。
```

非法参数、未初始化服务、过期句柄会报出诊断，失败前不取随机数。取流/抽取返回 `null`，洗牌返回 `ERR_INVALID_PARAMETER`（过期句柄为 `ERR_UNCONFIGURED`）；读档格式/版本不兼容返回 `ERR_INVALID_DATA`。版本配置缺失时服务返回 `ERR_UNCONFIGURED`；`begin_run()` 无法创建主种子时返回空字符串且保留旧上下文。发布版同样保留失败返回。调用方中止当前生成或结算，不暗中换流、用全局 RNG、发默认奖励或收费后重试。

候选 ID 池建议由业务按固定 ID 排序，再传入流。权重抽取的条目顺序也属于输入；牌组已有的真实顺序应保留，不应为“统一排序”破坏战斗存档。

`shuffle_in_place()` 会改传入数组本身。洗共享配置池前先 `duplicate()` 出局部列表；不要直接洗全局卡牌目录或其他模块仍在使用的候选池。仅改变列表顺序时浅复制足够，修改元素对象本身另由业务负责。

## 5. 业务怎么接

### 5.1 商店、奖励、事件：生成一次，展示多次

单局数据记录 `generated`、候选 ID 列表、价格/已售状态、已领取状态和次数。首次生成时取流、完成筛选/抽取后保存；以后重开界面直接读取该记录。

`get_stream()` 不负责判断商品是否生成过，不自动记住上次 `pick()` 的结果；将同一段生成代码再次运行，会继续取数并得到后续候选。这是调用方需避免的重抽。

刷新由对应业务在安全的同步结算段完成：先验证费用和合格池，使用新的 `occurrence` 生成并检查结果，然后一起提交次数、商品/奖励与费用。失败不收费、不递增业务次数；若已消费该次尝试的流，不能把失败当作从未发生并暗中重抽，报告失败并由业务处理。首版不提供通用随机事务/回滚框架。

### 5.2 战斗：洗牌使用流，发牌读取牌堆

```gdscript
# 仅在创建新战斗并需要洗牌时调用；加载已有战斗不执行这段。
var draw_rng = SeedService.get_stream(
    RandomDomains.BATTLE_DRAW, [map_id, node_id, battle_index], 0
)
if draw_rng == null:
    return  # 中止新战斗初始化，交由上层处理失败。
var draw_pile = deck_card_instance_ids.duplicate()
var error = draw_rng.shuffle_in_place(draw_pile)
if error != OK:
    return
# 将 draw_pile 写入战斗数据。
# 平常发牌按牌堆顺序取；弃牌堆重洗时继续使用 draw_rng。
```

发牌不必每张都再抽一个随机数。保存抽牌堆、弃牌堆、手牌与卡牌实例 ID；怪物随机使用 `battle.logic`，不推进抽牌流。UI 动画、预览、鼠标悬停不使用正式玩法流。

### 5.3 地图与新增玩法

地图在需要随机布局/模板选择时取得 `map.layout`；节点配比与位置分配取得 `map.nodes`。具体生成算法、连通性、锁路线关卡限制仍由地图系统执行，种子服务只提供随机数。非法布局重试必须有上限，由地图记录尝试号并对最终结果验收；服务不自动换主种子来回避失败。

药剂、素材合成或其他新系统可增加域，例如 `alchemy.result`。不要把一个通用的 `misc` 流供所有模块共用；也无需为每次取数创建一个新域。已有完整业务流程里的随机优先使用该流程自己的流。

## 6. 存档与恢复

### 6.1 必须一起保存的两部分

| 随机服务快照（PRG-005） | 业务存档（各业务 + PRG-003） |
| --- | --- |
| 快照格式版本、派生协议版本、主种子文本 | 地图实例/节点稳定 ID 与生成后的地图/节点数据 |
| 当前复现所用的实际引擎构建标识、项目内容版本 | 商店商品、价格/已售状态、刷新次数 |
| 已创建的每条流的地址、派生 seed、当前 state | 奖励候选、领取状态、奖励次数 |
| 地址中的 ID 类型和数值、`occurrence` | 战斗实例编号、牌堆/手牌/弃牌堆和其他战斗状态 |

只存主种子可以从头重建相同初始过程，不能让已经进行中的局回到准确进度。尚未创建的流不必存，恢复后仍可从原主种子与地址首次派生。局内已创建的流保留到结束，不因离开一个场景而删除。

快照结构示例（占位值不可用于读档）：

```json
{
  "snapshot_version": 1,
  "rng_protocol_version": 1,
  "engine_build": "<团队统一的实际构建标识>",
  "content_version": "<团队发布内容版本>",
  "main_seed": "jam-demo-001",
  "streams": [
    {
      "domain": "shop",
      "ids": [
        {"type": "string", "value": "map-001"},
        {"type": "string", "value": "hex:2,-1"}
      ],
      "occurrence": "0",
      "seed": "-245357105162270627",
      "state": "<从此RNG捕获的有符号64位十进制文本>"
    }
  ]
}
```

所有 64 位整数字段用十进制字符串保存，整数 ID 使用 `{"type":"int","value":"17"}`；恢复时按类型还原，不能把 `17` 变成 `"17"` 或 JSON 的浮点值。`snapshot_version` 等小版本号可使用 JSON 数值并严格校验整数。Godot JSON 文档指出数值解析经浮点转换，因此不用 JSON number 保存 RNG 的 64 位数值。[官方 JSON 说明](https://docs.godotengine.org/en/stable/classes/class_json.html#class-json-method-stringify)

整数文本先严格检查格式与范围，再转换：可为 `0`、无前导零的正整数或负整数，不允许 `+`、`-0`、小数、空白、额外字符或超出有符号 64 位范围；`occurrence` 另要求非负。不把解析失败当作 `0`。`state` 只来自服务捕获的 RNG 状态，不作为任意配置值填写；格式检查本身不能证明任意手写 state 是合法的 RNG 状态。

业务存档也要按自身结构校验并还原类型：例如 JSON 读回的 `battle_index`、刷新次数可能是 `float`，确认是范围内的整数后还原为 `int`，再传入服务。不要直接把浮点数放进 `ids`。较大的整数业务 ID 同样用带类型的字符串保存；优先采用稳定字符串节点 ID 可以减少这类转换。

### 6.2 恢复顺序

1. 存档负责人在无正在执行的随机结算的同步边界，捕获业务数据与随机快照，作为同一份局内存档提交。首版不在洗牌、刷新、奖励生成一半时保存；是否支持战斗中保存由战斗/存档负责人确认。
2. 读档前暂停输入与旧局业务。预先验证两部分数据与版本，保留失败时恢复旧局或返回菜单的处理能力。
3. `restore_snapshot()` 先在临时数据中验证格式、ID 类型、重复地址、seed/state 文本、版本和地址重新派生的 seed 是否一致；通过后整体替换随机上下文。失败不动现有服务。
4. 对恢复的每条 RNG，**先设置 seed，再设置捕获的 state**。Godot 设置 seed 会改变 state；不能逆序，也不能随便编造一个 state。[官方 RNG 说明](https://docs.godotengine.org/en/stable/classes/class_randomnumbergenerator.html)
5. 成功后载入业务状态、替换旧局对象、创建新业务场景；所有新对象重新 `get_stream()`。旧局与常驻 UI 的缓存句柄失效，不再使用。读档之后不再 `begin_run()`、重生成商品、额外洗牌或增加战斗编号。

整个读档由单局/存档负责人协调。`restore_snapshot()` 的 `OK` 只代表随机服务恢复成功；只有业务数据也成功安装，且新场景从这些数据恢复后，才能恢复输入并报告整局读档成功。中途失败时维持暂停，按协调者的恢复/返回菜单流程处理，不能让新随机状态搭配旧业务数据继续游戏。

“旧句柄失效”通过服务的运行代次检查实现：`begin_run()` 或成功恢复递增代次，包装对象调用时核对所属代次。该值是本地生命周期管理值，不参与派生、无需用于存档地址。业务负责人仍负责取消旧回调和定时任务，不能仅靠报错代替清理。

### 6.3 复现的实际承诺

相同主种子、派生协议、引擎构建、内容版本、业务输入与同一流的调用步骤，才能复现相同结果。不同系统的访问先后不影响彼此流的初始序列；同一业务调用更多随机，后续位置会变化。玩家决策改变池、权重、节点状态或牌组时，结果也可以变化。

首版对不兼容的引擎构建/内容版本存档明确返回失败，不静默从头派生。如何迁移旧局留到有实际发布需求时再设计。配置声明“4.7”尚不足以确定所有队友使用同一个二进制构建；联调时记录实际引擎版本与发布内容版本。Godot 将底层 RNG 算法视为实现细节，因此本次不承诺跨引擎升级的相同随机序列。[官方 RNG 说明](https://docs.godotengine.org/en/stable/classes/class_randomnumbergenerator.html)

## 7. 实现与兼容性

### 7.1 文件与配置

| 文件 | 职责 |
| --- | --- |
| `systems/random/seed_registry.gd` | 纯逻辑：地址编码、派生、缓存、快照验证与恢复 |
| `systems/random/random_stream.gd` | `RefCounted` 包装：一个 RNG、常用操作、句柄代次检查 |
| `systems/random/random_domains.gd` | 正式业务域常量；`class_name RandomDomains` |
| `autoload/seed_service.gd` | `Node`：同步入口与单局随机生命周期；Autoload 名称 `SeedService` |
| `project.godot` | `SeedService` Autoload 与 `application/config/seed_content_version` 内容版本 |

当前内容版本为 `jam-seed-v1`，位于 `project.godot` 的 `[application]` 下：`config/seed_content_version="jam-seed-v1"`。该配置随工程资源包导出，不需要为种子系统额外添加 `.txt` 导出过滤。服务首次使用时读取并固定版本，修改配置后重新启动游戏。修改会影响随机结果的规则、池、权重等发布内容时，由团队统一更新该版本；不热改运行中的版本配置。协议版本由模块常量管理，不由业务临时指定。

将模块接到其他工程时，复制 `systems/random/` 的三份脚本及 UID、`autoload/seed_service.gd` 及 UID，配置同名 Autoload，并设置非空的内容版本字符串。逻辑层可直接 `SeedRegistry.new("你的内容版本")`，但不要让各业务模块各建一个 registry 代替本局统一服务。

Autoload 脚本不再声明同名 `class_name SeedService`。业务使用基础服务的同步接口取得流，业务事件仍通过 `core/signals/` 通信；服务不引用商店、地图、战斗、UI 或状态机。更易独立测试的生成器可由装配层注入 `RandomStream`，不必在每个内部函数访问全局服务。Godot Autoload 可跨场景保留服务。[官方 Autoload 说明](https://docs.godotengine.org/en/stable/tutorials/scripting/singletons_autoload.html)

### 7.2 派生协议 v1

调用方不拼接地址、不计算 seed；本节供实现者固定协议，避免队友写出第二套不同的算法。

1. 主种子按第 3.3 节规范化，域与 ID 也按该节处理。
2. 字节前缀是 UTF-8 `spotlight-rng-v1` 后接一个 `0x00` 字节。
3. 后续字段顺序固定为：主种子（s）、域名（s）、ID 数量（i）、每个 ID、`occurrence`（i）。`s` 表示 UTF-8 字符串；`i` 的值是无前导零、无正号的整数十进制文本，零写 `0`。
4. 每个字段编码为 `类型字母 + 值的UTF-8字节长度的ASCII十进制文本 + 冒号 + 值的UTF-8字节`，直接连续拼接，不插空格。例：`"abc"` 为 `s3:abc`，整数 17 为 `i2:17`。字段中的冒号、逗号或中文不引起歧义。
5. 对全部字节计算 SHA-256，取摘要前 8 字节，按小端有符号 64 位解释，作为 Godot RNG 的 seed。负 seed 是合法的协议结果，不取绝对值、不再次截为 32 位。
6. 缓存使用完整规范地址字节的十六进制文本作为 key，不能只拿截断后的 seed 当地址。不同地址分别持有 RNG，即使其有限 seed 空间碰巧相同，也不能被缓存合并。

Godot 提供 SHA-256 的 `HashingContext`。[官方哈希接口](https://docs.godotengine.org/en/stable/classes/class_hashingcontext.html) 混合主种子与确定性身份派生流的思路也见 [NumPy 的多随机流说明](https://numpy.org/doc/stable/reference/random/parallel.html#sequence-of-integer-seeds)；这里借鉴寻址原则，不使用 NumPy 或声称本方案等同于其随机质量保证。

供派生实现核对的向量：主种子 `"jam-demo-001"`、域 `shop`、ID `["map-001", "hex:2,-1"]`、次数 `0`。

```text
canonical_hex = 73706f746c696768742d726e672d7631007331323a6a616d2d64656d6f2d30303173343a73686f7069313a3273373a6d61702d30303173383a6865783a322c2d3169313a30
sha256 = 5d48af47035198fcefb5274bf3953078597c0378b0fcc05c12b132b353b5cdad
derived_seed_signed64 = -245357105162270627
```

上述字节/摘要/seed 已用 Python 标准库核对，Godot 实现也已验证相同派生 seed 以及同 seed 序列、快照续接行为。协议已固定；改编码、字段顺序、摘要截取或包装取数规则均需升级协议。

### 7.3 首版范围与验证

已提供服务接口、四个流操作、稳定地址与快照。首版不做自动识别业务、固定 50 配额、通用随机事务、自研跨版本 PRNG、每次抽取的回放平台或大量逐模块包装类。空主种子输入时通过 `Crypto.generate_random_bytes(16)` 产生 128 位随机内容的十六进制文本；它不消费任何玩法流。新局负责人保存服务返回的主种子文本。

正式游戏随机不要直接使用 `randi()`、`randf()`、`randomize()`、全局 `seed()`、`Array.shuffle()` 或 `Array.pick_random()`。后两者使用全局 RNG；包装中的洗牌应使用自己的 RNG 做 Fisher–Yates，不能内部再调 `Array.shuffle()`。[官方 Array 说明](https://docs.godotengine.org/en/stable/classes/class_array.html#class-array-method-shuffle) 有界整数采用引擎的对应范围接口，不用 `随机数 % 数量` 代替均匀抽取。纯表现随机可另用本地表现 RNG，不纳入玩法服务。

| 检查 | 验收行为 |
| --- | --- |
| 同 seed 开新局 | 相同版本与输入产生相同初始序列 |
| 重复取同地址 | 得到同句柄并连续推进；取句柄本身不取数 |
| 不同访问顺序 / 新增域 | A/B 店调换访问顺序或额外调用新域，不改变既有流；测试固定池与条件 |
| UI 重开 | 商店/奖励结果与流 state 都不变 |
| 类型与编码 | 整数 ID 与字符串 ID 不串流，中文/分隔符地址无歧义，协议向量吻合 |
| JSON 往返 | seed/state、ID 类型与次数精确恢复，恢复后序列接续一致 |
| 读档与新局 | 老句柄不可继续取数；读档不重新洗牌/抽商品，失败恢复不改变原服务 |
| 非法输入 | 空池、负权重、全零权重、非有限权重、错误区间失败且不消费 RNG、不结算费用 |
| 权重缩放 | 相同比例的普通、极小与极大权重在相同随机序列下得到一致结果 |
| 场景与导出 | 跨场景流持续；团队目标导出构建通过复现与读档检查 |

已验证的证据包括：179 个核心行为断言、原地图自测回归、默认 PCK 资源包中服务初始化和 JSON 快照续接。独立本地小游戏的 30 个行为检查通过，实际图形渲染与按钮信号流程通过，涵盖商店/刷新、战斗/洗牌、奖励、JSON 存读档和胜败结算；验证脚本、小游戏和导出产物不纳入团队仓库。

当前只验证上述 macOS Godot 构建及 PCK 运行，未验证 Windows/Linux 可执行构建、引擎升级或团队正式玩法联调；`Mobile` 渲染后端不等于本模块已经做过手机平台验收。存档版本不兼容返回明确错误，不以重新开始一局冒充续档成功。
