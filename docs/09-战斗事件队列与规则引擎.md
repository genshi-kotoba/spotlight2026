# 战斗事件队列与规则引擎

战斗流程、卡牌效果、Buff 和典籍残片共用 `BattleStateMachine.rules`，不再各自通过同步信号回调推进结算。既有 `CardData` / `BuffData` 资源和 `EffectContext` 接口保留。

## 职责与数据流

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| `BattleEvent` | `core/battle/battle_event.gd` | 类型、载荷、元数据、事件 ID 与父/根事件 ID |
| `BattleEventQueue` | `core/battle/battle_event_queue.gd` | 非递归推进、暂停恢复、预算和历史记录 |
| `BattleRuleEngine` | `core/battle/battle_rule_engine.gd` | 按事件类型匹配条件，依优先级调用规则 |
| `BattleStateMachine` | `state_machines/battle/battle_state_machine.gd` | 战斗状态、公共变更方法、`flow.*` 流程续接 |
| `BattleEffectResolver` | `systems/cards/battle_effect_resolver.gd` | 加载资源，将卡牌/Buff 效果编译为事件 |
| `BattleEffectContext` | `systems/cards/battle_effect_context.gd` | 效果读取状态，写操作只提交指令 |
| `BattleStatRules` | `systems/buffs/battle_stat_rules.gd` | 动作执行时读取力量/虚弱等，修正数值 |
| `BattleActionRules` | `systems/cards/battle_action_rules.gd` | 把指令落实为状态变更 |
| `RelicBattleSystem` | `systems/relics/relic_battle_system.gd` | 注册事件触发与空间范围规则，提交典籍动作 |

典型伤害链路：

```text
flow.sequence.next
  → card.effect_requested
    → effect.execute（按资源 effects 顺序）
      → action.damage（数值规则 → 动作执行器）
        → combatant.damaged（事实 → 典籍反应）
        → flow.outcome（胜负判定）
  → flow.sequence.finish
  → 下一张牌 / 敌方回合
```

`action.*` 是尚未落实的指令；`combatant.damaged`、`card.drawn` 等是状态变更后发布的事实。请求信号只供兼容接口/UI 观察，系统效果不再监听这些信号执行，避免重复结算。

## 排序与推进

普通入队事件保持 FIFO；当前事件产生的子事件按发出顺序放在原续接点之前，子事件的反应也先完成。例如 A 产生 B、C，B 产生 D，原队列已有 E，实际顺序为 `A → B → D → C → E`。

这保证“获得力量 → 造成伤害”的伤害读取已经增加的力量；一次伤害引起的典籍连锁完成后才执行下一效果。不是“所有反应统一追加队尾”的顺序。

`publish()` 只入队，`submit()` 入队后尝试推进，`flush()` 推进已有事件。规则执行期间调用 `submit()` 只会入队，不会递归进入另一轮推进。普通战斗在调用内推进到空闲或输入暂停；UI 的每张牌 0.5 秒展示是单独重播表现，不是逻辑队列里的等待。

## 规则扩展

规则由稳定 ID、事件类型、处理器、优先级和可选条件组成。同一事件按优先级升序执行，同优先级按注册顺序执行。现有数值修正规则优先级为 10，动作执行器为 100。

例如在力量/虚弱修正之后，将对敌伤害上限限制为 5：

```gdscript
func attach(battle: BattleStateMachine) -> void:
    battle.rules.register_rule("custom.damage_cap", "action.damage",
        _cap_damage, 50, _targets_enemy)

func _targets_enemy(event: BattleEvent) -> bool:
    return event.payload.side == "enemy"

func _cap_damage(event: BattleEvent) -> void:
    event.payload.amount = mini(5, int(event.payload.amount))
```

处理器可以修改尚未执行的动作载荷，或者发布新的反应事件。重复 ID 会被拒绝；节点退出时应调用 `remove_rules_for(self)` 注销规则。新事件原语需增加上下文接口和对应动作执行规则；组合现有原语只需新增效果资源。

效果资源继续调用 `ctx.damage_enemy()`、`ctx.add_buff()` 等，不直接写生命/牌堆。执行阶段才读取当前 Buff；日志保留 `base_amount` 与最终 `amount`。自伤不受攻击加成影响，中毒绕过格挡并不受力量/虚弱影响，伤害下限为 0。

## 交互弃牌与终局

选择弃牌可以出现在 `CardData.effects` 任意位置：

```text
选择弃 1 → 获得 3 力量 → 伤害 8 → 再选择弃 1 → 治疗 5
```

请求时暂停整个队列，保留后续动作和流程。UI 提交准确数量、不重复且仍在手牌的 `instance_id` 后恢复；没有足量手牌时按现有数量请求，没有手牌则直接续接。连续两次选择各有独立请求；UI 必须先清理旧选择，再恢复队列，避免覆盖恢复时产生的新请求。

致死事实及其反应处理后判定胜负，并取消未执行的效果/流程；不会让后续治疗复活已判定败北的玩家。正在结算的卡仍发出一次 `card_resolved` 供表现使用。

## 循环保护与诊断

- 典籍：同一条因果路径同一触发格只进入一次；每根事件最多 128 个效果、128 个待处理典籍任务。超额只跳过该根的典籍效果，不清空正常流程。
- 指针：每张移位牌在一次出牌序列中只能改指针一次，重复请求也按来源限制；一段牌序最多结算 256 次。
- 队列：默认单次推进最多 50000 个事件，超额清空队列、发出 `limit_reached` 并返回 `ERR_CYCLIC_LINK`。`max_events_per_drain` 可用于低预算测试；异常规则应修复后重新开始测试战斗。

`rules.queue.history` 保留最近 2048 条事件快照，可通过 `JSON.stringify()` 输出；`id` / `parent_id` / `root_id` 用于追踪来源。`metadata.relic_ancestry` 保留典籍因果路径，`metadata.source_card` 保留卡牌来源；快照将资源转换为描述信息，不用于恢复事件执行。

存档增加 `queue_idle`。只允许 IDLE、PLAYER_ACTION 或终局等合法边界且队列空闲时恢复；输入暂停或有待处理事件的快照会被拒绝。旧快照缺少该字段时按原阶段校验兼容。当前不支持中途队列序列化恢复。

## 点击手牌问题与测试入口

实际复现为用户保存的典籍在首抽阶段击杀了原本 300 血的敌人；手牌仍显示，但战斗已结束，所以不能再编排。测试敌人默认改为可调的 3000 血，新增明确胜负提示和“重开战斗”，并按行动/交互阶段启用手牌按钮。玩家保存的典籍配置未修改。悬停放大仍为 1.5 倍，底边固定；加入出牌区显示尺寸仍为手牌的 1/2。

在 Godot 打开 `res://ui/battle/battle_test_scene.tscn` 按 F6。典籍入口为 `res://ui/relics/relic_test_scene.tscn`。

主要回归场景：

- `tests/battle_hand_input_selftest.tscn`：真实鼠标点击、悬停、取消、首抽终局与连续弃牌。
- `tests/battle_effect_rules_selftest.tscn`：伤害、治疗、格挡、Buff、指针与重复。
- `tests/relic_system_selftest.tscn`、`tests/relic_ui_selftest.tscn`：典籍规则与战斗 UI 接入。
- `tests/state_machine_selftest.tscn`、`tests/card_battle_integration_selftest.tscn`：回合流程、资源效果与存档集成。
