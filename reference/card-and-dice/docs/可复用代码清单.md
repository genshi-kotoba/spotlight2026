## 一、地图系统（PRG-011）

### 本项目要做什么

来自策划案与《回合外大地图形式和演出形式商讨》。

| 项 | 结论 |
| --- | --- |
| 格子 | **平顶六边形** |
| 视角 | 斜俯视角偏俯视 |
| 移动 | 操控角色点击移动，**无行动点消耗** |
| 结构 | 节点式路线，前进方向不受限 |
| 地形 | 有起伏，**相邻两格高度差绝对值超过阈值则不可通行** |
| 阻断 | 墙体阻断形成肉鸽式探索 |
| 迷雾 | **只显示当前能无阻通达的区域视野** |
| 节点类型 | 战斗、商店、随机事件 |
| 探索 | 自由探索，开出来的随机事件变为具体事件，具体事件与商店可重复探索，不强制立刻选择 |

工期不足时的退化方案是**用箭头指示位置代替角色移动**。

每局初始化三张地图。第一张为 3 个普通敌人、1 个精英、1 个 BOSS、7 至 9 个事件节点；第二张为 4 个普通敌人、2 个精英、1 个 BOSS；第三张策划案中未写全。

界面侧需要：通用事件面板与选项按钮、商店面板（商品展示、价格、买不起与已售出状态）、角色位置标识、迷雾与已探索区域。

### 能直接用什么

**`HexCoord`（181 行）用立方坐标做内部运算、偏移坐标做存储**，正是推荐的做法。可照搬的有：

- `ToCube` / `FromCube`：偏移与立方互转
- `CubeLerp`：两点插值。偏移坐标不能直接线性插值（会走出格子），必须先转立方。做平滑移动或投射物轨迹时用
- `TrySegmentFoot`：线段经过哪些格子，视线与范围判定用
- `RotateCcW60` / `RotateSteps` / `FormationSlot` / `RotateOffset`：旋转 60 度与编队摆放
- `NearestDirIndex` / `FacingSteps` / `DirDelta`：朝向与方向索引，做六方向朝向精灵和寻路转向
- `TryParseCell` / `FormatCell`：坐标序列化，存档与调试输出

**`HexMover` 有一条走通的交互链值得复刻**：

```
鼠标悬停某格 → 射线命中取出坐标 → 算路径 → 沿路径高亮并标注剩余点数
点击 → 再算路径 → 上移动锁 → 协程逐格移动 → 每到达一格更新当前坐标
     → 移动期间开相机跟随，结束关闭 → 通知回合管理器「移动已结束」
```

其中三处细节不能省：

1. **移动锁在点击瞬间置位**。原注释写的是「防止在协程启动前再次触发」。不做的话连点两下会启动两条移动协程，角色抽搐。
2. **相机跟随的开关时机**。移动开始时开启、结束时关闭，不是全程跟随。
3. **逐格清理**。走到一格就清那一格的高亮，不是全部走完再统一清，避免长路径下状态堆积。

**`VisionSystem.GetVisibleSet(from, range, ...)`** 返回 `HashSet<Vector2Int>`，实现的正是策划案要的「只显示能无阻通达的区域」。它已经处理了起点到目标是否被阻挡的判定。

**`EncounterZone.GroupConnected`** 做连通分量分组，迷雾按连通区域揭示、或划分遭遇区域时可以直接用。

### 要改什么

**通行谓词必须改成双参数。** 原工程是：

```csharp
bool IsPassable(Vector2Int coord)   // 只看目标格
```

本项目的通行依据是相邻两格高度差，只传一个坐标判不了：

```gdscript
func can_move(from: Vector2i, to: Vector2i) -> bool
```

连锁改动：寻路里的邻居判定、`HexMover` 的两处通行检查都要跟着改。**这是签名级改动，建议在写第一行代码前定死。**

**寻路建议改用 BFS。** 本项目没有行动点，所有可通行格代价相同，**图是无权的**；而「能无阻通达的区域」本身就是一次洪水填充。所以一次 BFS 同时给出可达集合（迷雾用）与最短路径（行走用）。

`AStarPathfinding` 里 `GetActionCost` 的加权、`CalculateDirectionCost` 的方向代价、开放集线性扫描，在本项目下都是死代码。188 行的 A\* 换成三十行左右的 BFS 即可。

**地形表要扩。** `TerrainManager` 现在没有高度概念，`TerrainData` 只有 `type / color / actionCost / passable`。本项目要加 `height`，并且 `Plain / Forest / Water / Mountain` 这套枚举是为骰子玩法定的，要按克苏鲁黑死病城市的场景重定。

**`WastelandGenerator` 不必整体移植。** 3136 行的规模远超本项目需要（每局三张图、节点从池中随机取）。但有两处值得参考：

- **`Generate(seed, settings)` 这个形状**正是 PRG-005「主种子派生 50 个子种子」需要的东西
- **`Settings` 配置对象**把生成参数集中成一个可复制对象，比散落的常量和序列化字段好维护

**`HexMeshFactory` / `HexRenderer` 不要。** 手工构造网格，Godot 用 `Polygon2D`、`TileMapLayer` 或 `MeshInstance2D`。

## 二、效果与 buff（PRG-007 / PRG-008）

### 本项目要做什么

**PRG-008** 要求 buff 包含三要素：**层数、持续回合数、效果**。全部写成公共可调用方法，执行时释放信号。

**PRG-007** 要求卡牌效果同理，且卡牌要素包含稀有度与效果。

**PRG-009 典籍残片**虽是独立系统，但接口约定与效果系统同源：**条件组件释放信号，效果组件必须收到信号才能启动**，且只有拼接界面里连在一起的组件才能传递信号。

### 原工程里有什么

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `EffectSystem/EffectData.cs` | 119 | `Effect` 抽象基类，三个枚举 |
| `EffectSystem/Effects.cs` | 383 | `EffectFactory` + 十一个具体效果 |
| `EffectSystem/EffectManager.cs` | 429 | 实例管理与回合钩子 |
| `EffectSystem/EffectUtils.cs` | 31 | 按名建实例 |

抽象基类的方法集：

```
Apply(target, stacks)
End(target)
OnTurnUpdate(target, currentStacks) -> int
GetEffectStrength(stacks) -> float
```

已实现的效果：护甲、虚弱、力量、治疗、行动、移动点削减，以及骰子面值修正相关的四个（Floor/Ceil 的 Modifier、Duration、Stance）。

`EffectManager` 除了增删查，还有几个能看出设计意图的方法：

```
GetDiceFaceModifiers(target, out floorBonus, out ceilBonus)
ClearStances(target, reason)
ConsumeRollModifiers(target)
ReduceEffectStacks(target, effectTypeName, amount)
```

### 能直接用什么

三要素与原作完全对应，**缺的只有一条：执行时释放信号**。

`EffectApplyTiming` 枚举区分生效时机的设计保留。`OnTurnUpdate` 返回 `int` 用于回合结算时递减层数，治疗与行动两个效果重写了它，可以照着写。

### 要改什么

- `EffectManager` 的单例改为 autoload，且只放实例管理，不放业务逻辑
- `Apply` / `End` / `OnTurnUpdate` 三处执行后各释放一个信号
- 目标从 `GameObject` 改为 `instance_id` 或轻量句柄，避免强引用节点生命周期
- `EffectUtils.CreateEffectInstance(string)` 用字符串匹配类型，拼错编译期发现不了，改用类型引用或枚举

## 三、动作与反应框架（PRG-007）

### 本项目要做什么

PRG-007 要求「卡牌效果全部写成公共可调用方法，执行时释放信号」。

### 原工程里有什么

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `ActionSystem/GameAction.cs` | 25 | 动作抽象基类 |
| `ActionSystem/ActionSystem.cs` | 211 | `AddReaction(action)` / `Perform(action, onFinished)` |
| `ActionSystem/ReactionTiming.cs` | 15 | 反应时机枚举 |

| `ActionSystem/Systems/*` | 514 | 牌堆、伤害、能量、出牌、状态五个子系统 |

**这块是本项目没有、但值得整体借鉴的设计。**

### 能直接用什么

按这套拆，卡牌效果不需要各自实现一遍流程控制，只要产出 `GameAction` 交给统一执行器。这正好满足 PRG-007「公共可调用方法 + 释放信号」的要求，而且比让每个效果自己管流程更符合低耦合。

## 五、局内外状态（PRG-002 / PRG-003 / PRG-004）

### 本项目要做什么

**PRG-002 全局状态机**：管理局外存档 —— 成就、解锁卡牌、对局记录、已保存设置。**存档采用 JSON**，每局游戏结束后以及游戏关闭时自动写入，打开游戏自动读取。

与局内状态机的关系：

- 局内状态机初始化时从这里读卡牌解锁列表，只把已解锁的卡加入本局卡池
- 全局状态机监听局内状态机的 update 事件，据此检测成就
- 设一个布尔值表示是否正在对局中，有对局时保存会一并保存局内状态机

**PRG-003 局内状态机**：管理地图、玩家状态、牌组、道具。

初始化流程是载入随机种子，生成地图、奖励池、商店池、随机事件池。需要存储和更新的内容：玩家血量、血量上限、金币、牌组、持有道具、经历战斗数、已击败敌人、每个地图节点的状态。每个可能触发成就的数值携带一个 update 方法。

**PRG-004 战斗状态机**：管理主角状态、怪物状态、buff 结算、抽牌弃牌、怪物行动模式。

回合制，**抽牌、弃牌、牌效执行、buff 结算都是一个一个来，每次执行都放出信号**。

```
己方回合：抽牌 → buff 结算 → 出牌 → 牌效结算
对方回合：决定行动 → buff 结算 → 行动
```

牌在抽牌堆与弃牌堆之间流转，抽牌堆为 0 时把弃牌堆洗入。

### 原工程里有什么

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `Meta/MetaWallet.cs` | 879 | 存档主体：材料、灵魂、配方、被动、配装快照 |
| `Meta/SaveSlots.cs` | 172 | 多存档槽读写 |
| `Meta/LoadoutDistribution.cs` | 186 | 开局配装分配 |
| `Game/GameStateManager.cs` | 116 | 探索 / 战斗 / 暂停三态 |
| `Game/TurnManager.cs` | 782 | 战斗回合 |
| `Game/UnitOccupancy.cs` | 196 | 格子占位管理 |
| `ExplorationSystem/ExplorationTurnManager.cs` | 956 | 探索态回合 |

### 能直接用什么

**`MetaWallet`** 内部的 `SaveData` 结构、`NamedStack`（带名字的堆叠）、`LoadoutSnapshot`（配装快照）都是可借鉴的数据模型。`SaveSlots.PathFor(slot)` / `TryRead` / `Clear` 是多存档槽的现成实现，与本项目「JSON 存档」的要求一致。

**`UnitOccupancy`（196 行）值得单独看**：统一管理「哪些格子被占了」，提供 `IsOccupied` / `GetOccupiedTiles` / `IsBlockedForEnemyTransit`，还有 `PatrolLandingClaims` 子类做「本回合临时占位声明」。本项目战斗如果也在六边形地图上打，这套并发占位管理绕不过去。

### 要改什么

`TurnManager` 的公开接口形状可用：

```
StartNewTurn(bool preservePlayerArmor)
EndPlayerTurn() / OnMoveEnded() / OnPlayerStepped()
BeginBattleFromExploring(bool enemySurprise)
IsPlayerTurn() / IsEnemyTurn() / GetCurrentTurn()
```

骰子相关的 `GetPlayerDiceCount` / `ConsumeDice` / `CanSpendDiceForAP` / `RecordDiceForAP` 删掉。

但**实现要重写**：原作是单例加直接方法调用，本项目要求逐个执行并释放信号，改成 `turn_started` / `phase_changed` / `turn_ended` 驱动。

`GameStateManager` 的 `GameState` 枚举（探索 / 战斗 / 暂停）对应 PRG-003，但本项目要管的东西更多（地图、玩家、牌组、道具、随机种子），只借鉴状态划分思路。

## 七、随机种子（PRG-005）

### 本项目要做什么

用 PRNG 生成主种子，地图使用主种子生成，再从主种子**派生 50 个子种子**，分别用于奖励池、商店池，以及每一场战斗的抽牌顺序。

### 原工程里有什么

没有独立的种子模块，但 `WastelandGenerator.Generate(int seed, Settings s)` 是种子式生成的现成形状，`System.Random rng` 的用法可以参考。

### 要改什么

本项目需要的只是**派生与持有 50 个子种子**，比程序化生成简单得多。设计上要保证：同一主种子复现同一局，且各子系统的随机流互不干扰。

## 附录：六边形坐标公式

原作用 **odd-q 偏移坐标**存储、立方坐标运算。本项目已确定**平顶六边形**，建议沿用同一套做法：逻辑层用轴向坐标，只在需要矩形存储时转换。

轴向转像素（`size` 为外接圆半径）：

```
x = size * 1.5 * q
y = size * sqrt(3) * (r + q * 0.5)
```

像素转轴向：

```
q = (2.0 / 3.0 * x) / size
r = (-1.0 / 3.0 * x + sqrt(3) / 3.0 * y) / size
```

六个邻居（轴向的邻接方向与朝向无关）：

```
(+1, 0)  (+1, -1)  (0, -1)  (-1, 0)  (-1, +1)  (0, +1)
```

距离：

```
maxi(abs(q1 - q2), abs(r1 - r2), abs((q1 + r1) - (q2 + r2)))
```

对比原作的分奇偶两分支写法（`AStarPathfinding` 里那两套 `oddOffsets` / `evenOffsets`），邻接变成一张常量表，距离变成一行。
