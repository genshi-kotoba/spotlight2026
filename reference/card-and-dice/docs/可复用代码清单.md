## 一、六边形坐标（PRG-011 地基）

**`EnemySystem/HexCoord.cs`，181 行。这是全仓复用价值最高的单个文件。**

它用**立方坐标**做内部运算，偏移坐标做存储，正是推荐的做法。

```
Cube ToCube(Vector2Int offset)
Vector2Int FromCube(Cube c)
Cube CubeLerp(Cube a, Cube b, float t)
bool TrySegmentFoot(Vector2Int from, Vector2Int a, Vector2Int b, ...)
Cube RotateCcW60(Cube c)
Cube RotateSteps(Cube c, int steps)
Vector2Int RotateOffset(Vector2Int offset, int steps)
Vector2Int FormationSlot(Vector2Int anchor, Vector2Int templateOffset, int faceSteps)
int NearestDirIndex(Cube delta)
int FacingSteps(Vector2Int from, Vector2Int to)
int DirDelta(int fromIndex, int toIndex)
bool TryParseCell(string text, out Vector2Int cell)
string FormatCell(Vector2Int cell)
```

可以照搬的部分：

- `ToCube` / `FromCube`：偏移与立方互转，本作直接可用
- `CubeLerp`：两点间插值，做角色沿边移动的平滑曲线、或者投射物轨迹时用得上
- `TrySegmentFoot`：线段经过哪些格子，做视线判定和范围判定时会用到
- `RotateCcW60` / `RotateSteps`：旋转 60 度，编队时摆朝向用
- `FacingSteps` / `DirDelta` / `NearestDirIndex`：朝向与方向索引，做六方向朝向精灵和寻路转向时用
- `TryParseCell` / `FormatCell`：坐标字符串序列化，做地图存档和调试输出时用

`FormationSlot` 与 `RotateOffset` 是编队专用的，本作如果敌人不摆阵就不需要，但可以看看它的写法。

Godot 里 `Vector2Int` 对应 `Vector2i`，`Cube` 这个 struct 直接翻译成 GDScript 的 `Dictionary` 或一个轻量 `RefCounted` 类即可。

### 值得先看的两个文件

**`VisionSystem.cs`** 提供 `GetVisibleSet(from, range, greenPenalty)` 与 `ComputeVisibleSet(...)`，返回 `HashSet<Vector2Int>`。本作策划案写的是「迷雾设计，只显示当前能无阻通达区域视野」——这正是同一类计算。它的实现里已经处理了「起点到目标是否被阻挡」的判定，可以参考它的遮挡处理方式。

**`EncounterZone.GroupConnected`** 做的是连通分量分组。本作如果迷雾按连通区域揭示，或者要做「遭遇区域」划分，这段逻辑可以直接用。

### 寻路：本作建议改用 BFS

`AStarPathfinding` 现在 420 行，签名已经扩展到支持占位与规划预留：

```csharp
FindPath(start, target, allowOccupiedTarget, enemyRequester, planningReserved)
```

但 spotlight2026 的规则是「高度差绝对值超过 N 则不可通行」，这是二值判定，**图无权**。同时迷雾要求「能无阻通达的区域」，本身就是一次洪水填充。所以：

- 一次 BFS 同时给出可达集合（迷雾用）和最短路径（行走用）
- A\* 的启发式在无权图下退化为 0，加权逻辑与方向代价都用不上

这不是说不能移植 A\*，而是移植过来有一半是死代码。

### 地形通行谓词要改签名

`TerrainManager` 现在仍是单参数：

```csharp
bool IsPassable(Vector2Int coord)
```

本作要判高度差，必须变成双参数：

```gdscript
func can_move(from: Vector2i, to: Vector2i) -> bool
```

连锁改动：寻路里的邻居判定、`HexMover` 的两处通行检查都要跟着改。这是签名级改动，建议在写第一行代码前定死。

另外 `TerrainManager` 当前没有高度概念，`TerrainData` 只有 `type / color / actionCost / passable`，本作要加 `height`，并且地形枚举要按克苏鲁黑死病城市重定。

### `WastelandGenerator` 3136 行

这是程序化荒野生成器，含七个生物群系（Grass / Jungle / Cave / Ruins / AncientForest / Swamp / WildVillage）、`Settings` 配置对象、`Generate(int seed, Settings s)` 入口、`WastelandLayout` 输出结构。

本作的 PRG-011 写的是「每局初始化三张地图，节点从对应池中随机取」，规模比它小得多，不需要整个移植。但有两个地方值得参考：

1. **种子式生成**。`Generate(seed, settings)` 这个形状正是 PRG-005「主种子派生 50 个子种子」需要的东西
2. **`Settings` 配置对象**。把生成参数集中成一个可复制的配置对象，比散落的常量和 `[SerializeField]` 好维护

- 保留 `EffectApplyTiming` 区分生效时机的设计

## 四、动作与反应框架（PRG-007）

**这块是 spotlight2026 没有、但值得整体借鉴的设计。**

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `ActionSystem/GameAction.cs` | 25 | 动作抽象基类 |
| `ActionSystem/ActionSystem.cs` | 211 | `AddReaction(action)` / `Perform(action, onFinished)` |
| `ActionSystem/ReactionTiming.cs` | 15 | 反应时机枚举 |
| `ActionSystem/Actions/*` | 155 | 六个具体动作：加状态、消耗能量、造成伤害、弃牌、抽牌、出牌 |
| `ActionSystem/Systems/*` | 514 | 牌堆、伤害、能量、出牌、状态六个子系统 |

它的核心思路是：**一切游戏行为都是一个 `GameAction` 对象，交给 `ActionSystem.Perform` 执行，执行完回调**。这样出牌、伤害、抽牌、加状态走同一条管道，日志、动画、成就检测都只需要挂在一个地方。

对本作的价值：PRG-007 要求「卡牌效果全部写成公共可调用方法，执行时释放信号」。如果按这套拆，卡牌效果不需要各自实现一遍流程控制，只要产出 `GameAction` 交给统一的执行器即可。

## 五、卡牌（PRG-013 / PRG-014）

| 文件 | 行数 | 内容 |
| --- | --- | --- |
| `CardSystem/Card.cs` | 292 | 运行时卡牌实例，含骰子绑定 |
| `CardSystem/CardData.cs` | 557 | 卡牌静态数据 |

| `CardSystem/CardPileManager.cs` | 274 | 抽牌堆/弃牌堆 |
| `CardSystem/TacticSlotRuntime.cs` | 606 | 战术槽（本作无对应系统） |
| `CardSystem/CardView.cs` | 1216 | 单卡表现，Godot 重写 |
| `CardSystem/CardDeckManager.cs` 等 | — | — |

**数据与实例分离**是这套设计的关键：`CardData` 是静态配置，`Card` 是运行时实例。本作应当沿用这个划分。

`CardData` 提供：

```
List<DiceData> GetBoundDice()
int GetSuitCount(SuitOption suit)
static string GetDiceValueColorHtml(int value, DiceData dice)
string GenerateDynamicDescription(int[] diceValues)
string GenerateDynamicDescription(int[] diceValues, List<ComputedValueSegment> segments)
```

`GenerateDynamicDescription` 按数值动态拼描述文本，并支持分段计算（`ComputedValueSegment`）。本作 PRG-014 可以直接借鉴。

枚举要重定：`SuitOption`（花色）、`DiceSelect`（骰子选择）、`CardEffectType` 都服务于骰子机制，本作没有骰子，要换成出牌区指针与位移逻辑。

存储上原作是 `ScriptableObject`，本作对应 `.tres`；批量卡牌数据按项目约定走 `data/cards/` 下的 csv。

## 十、移植顺序建议

按依赖排，前两项零依赖、纯逻辑、可以直接单测：

1. `hex_coord.gd` —— 从 `HexCoord` 翻译，无依赖
2. `effect.gd` / `effect_instance.gd` —— 从 `EffectData` 翻译，独立可测
3. `map_tile.gd` / `map_terrain.gd` —— 地图数据层，依赖坐标，加高度
4. `effect_manager.gd` —— 效果管理器，接上信号
5. `map_reachability.gd` —— BFS，依赖数据层
6. `player_mover.gd` / `map_input.gd` —— 交互层，依赖 BFS
7. `card_data.gd` —— 卡牌数据模型，枚举按本作重定

对应本作排期：第 1、3、5、6 项属第一周的 PRG-011；第 2、4 项属第二周的 PRG-008，其基类可在第一周先落。
