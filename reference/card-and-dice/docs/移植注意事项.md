# 移植注意事项

本文写给要把这份参考里的代码搬去 spotlight2026 的人。**先读这篇，再动手抄代码。**

代码是 Unity + C#，目标是 Godot 4.7 + GDScript。算法可以直接翻译，但下面几类写法必须改，否则会把坏味道带过去。

本项目每个系统要做什么、对应原工程的哪个文件，见 [可复用代码清单](可复用代码清单.md)。两份文档配合看：那份回答「抄什么」，这份回答「怎么抄才不出事」。

## 一、语言与引擎的对应关系

| Unity / C# | Godot / GDScript |
| --- | --- |
| `MonoBehaviour` | `Node` |
| `Vector2Int` | `Vector2i` |
| `Vector3` / `Vector2` | 同名 |
| `ScriptableObject` | `Resource`（`.tres`） |
| `[SerializeField]` | `@export` |
| `Start()` / `Awake()` | `_ready()`（顺序语义不同，见下） |
| `Update()` | `_process(delta)` |
| `IEnumerator` 协程 | `await` 与信号 |
| `Instantiate` | `instantiate()` |
| `Destroy` | `queue_free()` |
| `FindObjectOfType<T>()` | 不要用，改为注入或 autoload |
| `GameObject.Find("名字")` | 不要用，改为场景引用 |
| `Physics.Raycast` | `PhysicsDirectSpaceState2D.intersect_ray` 或 `Control` 的输入事件 |
| `EventSystem.IsPointerOverGameObject()` | `Control.mouse_filter` |
| `DOTween` | `Tween` |
| `TextMeshPro` | `Label` + 主题 |
| `OnValidate()` | `@tool` + `_validate_property()` |
| `PropertyDrawer` | `@tool` 脚本或 `EditorInspectorPlugin` |

两个语义差异要注意：

**生命周期顺序**。Unity 的 `Awake` 全部先于任何 `Start`；Godot 的 `_ready()` 是自下而上（子节点先于父节点）。依赖「先收集全部单例再初始化」的代码不能直接翻译，要改成显式初始化或 `call_deferred`。

**协程与线程**。Unity 的 `IEnumerator` 协程可以直接写成 `await`，但 `yield return null`（等一帧）与 `await get_tree().process_frame` 不完全等价，逐帧逻辑要重看。

## 二、必须改掉的耦合写法

### 1. 静态单例

原工程有 `Core/Singleton.cs` 提供 `SingletonBase`，说明作者已经意识到这个问题。但仍有大量类用静态 `Instance`：

```csharp
public static EffectManager Instance { get; private set; }
CameraController.Instance?.StartFollowingPlayer();
TurnManager.Instance?.OnMoveEnded();
```

**问题**：调用方看不出自己依赖了谁，测试时无法替换，初始化顺序一变就空引用。

**改法**：状态机本体可以用 Godot 的 autoload，但职能要窄。纯粹的协作者（比如地形查询、占位查询）应当通过 `@export` 注入或从场景树显式获取一次并缓存。判断标准是：**这个依赖能不能在编辑器里看到？** 看不到就是隐式的，要改成看得见的。

### 2. 从物体名解析坐标

```csharp
if (name.StartsWith("Hex_")) {
    string[] parts = name.Split('_');
    coordinates = new Vector2Int(int.Parse(parts[1]), int.Parse(parts[2]));
}
```

**问题**：改名即失联，而且每次都要字符串解析。批量改名、编辑器里改层级、导入导出都会踩。

**改法**：坐标存成真实字段。`HexTile` 现在有了 `static Vector2Int CoordOf(GameObject tile)`，说明作者也在往这个方向收，但本质仍是名字解析。Godot 里用 `@export var coord: Vector2i` 或者由地图对象统一持有 `Dictionary[Vector2i, Node]`。

### 3. 沿父链查找特定名字

```csharp
bool IsTileInMap(GameObject tile) {
    Transform parent = tile.transform.parent;
    while (parent != null) {
        if (parent.name == "Map") return true;
        parent = parent.parent;
    }
    return false;
}
```

**问题**：场景层级一挪就失效，而且每次调用都要走一遍父链。

**改法**：由地图对象直接持有格子集合，判定变成一次字典查找。

### 4. 遍历子物体做线性查找

```csharp
foreach (Transform child in mapObject.transform) {
    if (child.name == $"Hex_{coord.x}_{coord.y}") return child.gameObject;
}
```

**问题**：单次 O(n)，而它常被按路径逐格调用，整体 O(n²)。地图一大就卡。

**改法**：建 `Dictionary[Vector2i, Node]` 索引，O(1)。

### 5. 用字符串匹配类型

```csharp
public static Effect CreateEffectInstance(string effectTypeName)
```

**问题**：拼写错误编译期发现不了，重构改名也没有工具支持。

**改法**：用类引用、枚举，或者 Godot 的 `Resource` 直接实例化。

### 6. 用 `GameObject` 当数据键

效果系统用 `GameObject target` 标识作用对象。

**问题**：强引用节点生命周期，节点释放后字典里会留悬空键；也无法序列化存档。

**改法**：用 `instance_id`、或者一个业务层的实体 ID。存档要跨会话，`instance_id` 也不合适，最终应当有自己的实体标识。

### 7. 硬编码颜色与数值

`HexTile` 用 `switch` 把地形类型映射成颜色，`TerrainManager.InitializeTerrainTypes` 里把颜色、代价、通行性写死在代码里。

**问题**：改配色要改代码，策划调数值也要找程序。

**改法**：走配置资源。Godot 里用 `.tres` 定义地形类型表，代码只负责查表。

### 8. 表现与状态混在一起

`HexMover` 1008 行里同时有：输入处理、路径预览、高亮着色、文本创建、移动协程、相机控制、行动点结算。

**问题**：改任何一处都要读完整文件；测试时没法只测移动逻辑。

**改法**：拆。至少分成输入层（悬停与点击分发）、路径层（算路与预览数据）、移动层（沿路径行走与相机跟随）。Godot 里这三个可以分别是三个节点，通过信号连接。

## 三、本项目特有的规则

这几条与原设计的差异，不是代码洁癖，是玩法不同导致的。

### 通行判定要改成双参数

原工程：

```csharp
bool IsPassable(Vector2Int coord)
```

只看目标格。spotlight2026 的规则是「相邻两格高度差绝对值超过 N 则不可通行」，必须知道来源格：

```gdscript
func can_move(from: Vector2i, to: Vector2i) -> bool
```

### 图是无权的，A\* 有一半用不上

原工程 `AStarPathfinding` 420 行，里面有：

- `GetActionCost` 参与权重
- `CalculateDirectionCost` 做方向代价，鼓励直线
- 开放集线性扫描找最小 f 值

spotlight2026 没有行动点，所有可通行格代价相同，是**无权图**。加上迷雾要求「显示能无阻通达的区域」，本身就是一次洪水填充。所以：

**一次 BFS 同时给出可达集合（迷雾）和最短路径（行走），比 A\* 少一套代码还多一份结果。**

不是不能移植 A\*，是移植过来有一半是死代码。

### 没有行动点

原工程的 `currentActionPoints` / `maxActionPoints` / `ShowAPText` / `CanSpendDiceForAP` / `RecordDiceForAP` 这套东西，spotlight2026 全部不需要。删的时候注意别把相邻的清理逻辑一起删了——比如 `MoveSequence` 里「走一格清一格高亮」不依赖行动点，要留下。

## 四、值得保留的细节

抄代码时这几处不要漏，它们是踩过坑才写出来的。

**移动锁**。点击瞬间就置 `isMoving`，注释写的是「防止在协程启动前再次触发」。不做的话连点两下会启动两条移动协程，角色来回抽搐。

**相机跟随的开关时机**。移动开始时开启、结束时关闭，而不是全程跟随。全程跟随会让相机在待机时也跟着鼠标乱动。

**逐格清理**。走到一格清掉那一格的高亮，而不是全部走完再统一清。长路径下后者会积累大量状态。

**`HexCoord.CubeLerp`**。偏移坐标不能直接线性插值（会走出格子），必须先转立方坐标再插值。做平滑移动或投射物轨迹时要走这条。

**`UnitOccupancy` 的临时占位声明**。`PatrolLandingClaims.Begin/End/Claim/CanStop` 处理的是「多个单位同回合移动时，如何避免同时选到同一格」。如果 spotlight2026 的敌人也在同一张六边形地图上移动，这个并发问题是绕不过去的。

**`HandUIController` 的 partial 拆分**。一个类拆成六个文件（Arrow / CheckAssist / Hover / Interaction / Layout / PlayAnimation），按职责切分而不是按大小。GDScript 没有 partial，但可以拆成多个协作的节点或组合对象。

## 五、不要照搬的

| 内容 | 原因 |
| --- | --- |
| `Editor/` 下 23 个脚本 | Unity Inspector 扩展，机制完全不同 |
| `HexMeshFactory` / `HexRenderer` | 手工构造网格。Godot 有 `Polygon2D`、`TileMapLayer`、`MeshInstance2D` |
| `DOTween` 的调用 | Godot 用 `Tween`，API 不同 |
| `InventoryUIKit` 那套纯代码建 UI | Godot 用场景 + `Control` 节点，代码建界面反而难维护 |
| 全部骰子相关 | `DiceSystem/`、`CardLoadout`、`DicePayment`、`CardRerollButton` 等，本作没有骰子 |
| `Tutorial/` 六个脚本 | spotlight2026 第一版不做教程 |
| `Dev/DevPanel.cs` | 开发调试面板，与本作无关 |

## 六、抄之前的问题清单

对着代码问一遍，答不上来就先别抄：

1. 这个类依赖了哪些 `Instance` 或 `FindObjectOfType`？改成注入要动几处？
2. 它有没有从物体名或父链里推导信息？改成显式字段要动几处？
3. 它把哪些数值或颜色写死在代码里？这些在本作该放哪个配置？
4. 它一个文件里干了几件事？拆成几个合适？
5. 它的公开方法是「做什么」还是「怎么做」？接口形状够不够窄？
